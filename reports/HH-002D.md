# HH-002D: 360px mobile + accessibility review (read-only)

Scope read strictly to: `src/app/globals.css`, `src/components/*.tsx`, `src/app/**/page.tsx`.
Out of scope (not read): `src/app/layout.tsx`, `src/lib/*`, `.env.local`.

## Findings

### 1. Edits are not saved as drafts — in-progress edits are lost on reload/navigation
- Location: `src/app/edit/page.tsx:45` (no `draftKey`); compare `src/app/new/page.tsx:33`
  (`draftKey="draft:new-skill"`).
- Problem: `SkillForm` only persists drafts when given a `draftKey`
  (`SkillForm.tsx:24`, save at `:46`). `EditPage` omits it, so edits live only in React
  state. On page reload or navigation away the in-progress text is gone; the form re-fetches
  the last server version. This breaks the "half-written form must survive a lost connection"
  requirement.
- Affects: anyone editing a listing on a 360px phone who leaves the page before saving.
- Fix: pass `draftKey="draft:edit-skill"` to the `<SkillForm>` in `EditPage`, and change the
  restore effect (`SkillForm.tsx:27-32`) so it no longer early-returns when `initial` is set —
  instead prefer a saved draft over the fetched `initial`.
- Note: the missing prop is verified; whether `useDraft(undefined)` silently no-ops vs. throws
  cannot be confirmed (`src/lib/useDraft` is out of scope).

### 2. Edit-page fetch error offers no retry (flaky mobile network)
- Location: `src/app/edit/page.tsx:39` (`if (error) return <ErrorState message={error} />;`).
- Problem: the error branch passes no `onRetry`, unlike `src/app/page.tsx:67`
  (`onRetry={retry}`) and `src/app/mine/page.tsx:45` (`onRetry={load}`). A timed-out fetch on a
  weak connection errors out with no in-place recovery.
- Affects: any mobile user whose listing load fails mid-fetch.
- Fix: add `const [attempt, setAttempt] = useState(0);` in `EditInner`, add `attempt` to the
  effect deps (`page.tsx:34`), and pass `onRetry={() => setAttempt((a) => a + 1)}` to the
  `ErrorState`. Small, self-contained.

### 3. Could not verify the viewport meta tag (out of scope)
- Location: not readable — the viewport lives in `src/app/layout.tsx`, which the prompt bars.
- Problem: the whole 360px analysis assumes `width=device-width, initial-scale=1`. If the
  viewport is missing or fixed to a desktop width, the app renders wide and every layout
  conclusion here is void.
- Affects: everyone on 360px — the most mobile-critical item cannot be confirmed from the
  permitted files.
- Fix (in-scope owner): ensure `layout.tsx` (or `generateViewport`) sets
  `<meta name="viewport" content="width=device-width, initial-scale=1" />`.

## Verified OK (no issues found)
- Touch targets >= 44px: `.nav-link` min-height 44px (`globals.css:31`), `.btn` 48px (`:48`),
  `.kind-option` 52px (`:60`), `input/select/textarea` 48px (`:39`).
- No horizontal scroll at 360px: `body overflow-x:hidden` (`:18`), `.shell-main` padding 1rem
  / max-width 640 (`:33`), inputs `width:100%` (`:38`), `.card overflow-wrap:anywhere` (`:68`),
  `flex-wrap` on `.shell-header`/`:kind`/chips/`.row`. No fixed width exceeds the viewport.
- Loading / empty / error states explicit on BrowsePage, MySkillsPage, NewSkillPage,
  EditPage, and SkillCard.
- New-skill draft survival is solid: autosave on each change (`SkillForm.tsx:46`), one-time
  restore (`:27-30`), submit disabled offline (`:103`), `draft.clear()` only on success (`:55`).
