# HH-002E Report — Red-team Assessment of RLS Policies on public.skills

## Scope and Method

Read-only red-team assessment. No database connection was made; no files were edited.
All findings are from static analysis of the following files:

- `supabase/migrations/20261004_create_skills.sql` — schema, RLS policies, indexes
- `supabase/migrations/20261007_protect_phone_add_kind.sql` — column-level grants, `kind` column
- `src/lib/skills.ts` — application query functions (fetchSkills, fetchSkill, fetchPhone, createSkill, updateSkill, setWithdrawn, fetchMySkills)
- `SECURITY.md` — security checklist and prior test results (2026-10-10, dev Supabase project)

Each finding includes: the policy or line involved, attack steps, risk rating, and a proposed fix.
Findings are ordered by severity, high to low.

## Findings

### 1. Phone number scraping by signed-in users — HIGH

**Policy / line involved:**

- Migration 20261004, policy "anyone can read active skills" (lines 16-20):
  ```sql
  for select to anon, authenticated using (status = 'active');
  ```
  This policy grants `authenticated` users SELECT on every column of every active row —
  including `phone_number`.
- Migration 20261007 (lines 13-15): `revoke select on public.skills from anon` then
  `grant select (col1, col2, ... without phone_number) on public.skills to anon`.
  Only `anon` was restricted. The `authenticated` role retains table-level SELECT on
  all columns, including `phone_number`.
- `src/lib/skills.ts`, `fetchPhone` (lines 81-85): queries
  `.select("phone_number").eq("id", id).single()` with no rate limit, no per-user
  quota, and no audit trail.
- `src/lib/skills.ts`, `fetchSkills` (lines 45-61): returns 50 listings per page with
  no maximum offset, enabling full enumeration of all listing IDs.

**Attack (step by step):**

1. Sign in to the app with any valid account (even a throwaway).
2. Call `fetchSkills({ ... })` repeatedly, incrementing the page offset by 50 each
   time. Because there is no maximum offset, every active listing ID in the table can
   be enumerated.
3. For each listing ID obtained, call `fetchPhone(id)`. The database returns
   `phone_number` because:
   a. RLS policy "anyone can read active skills" satisfies the `status = 'active'`
      condition for every active listing.
   b. The `authenticated` role has table-level SELECT on all columns (migration
      20261007 only revoked and re-granted column-level SELECT for `anon`;
      `authenticated` was never restricted).
4. Compile a complete phone-number directory of every active listing in the system.
   No rate limiting, pagination cap, or access logging prevents this.

**Why this is a problem:**

Phone numbers are PII. The intended rule is "signed-in users may read phone numbers
of visible listings" — but "visible listings" is not bounded. Any authenticated user
can scrape every phone number in the table. SECURITY.md confirms (line 20):
"signed-in users can read phone_number" — this is the exact enabler.

**Risk:** HIGH — PII (phone numbers) exposed to any authenticated user with zero
friction or controls.

**Proposed fix:**

- Add a per-user rate limit on `fetchPhone` calls (e.g., max 10 lookups per hour
  per UID), enforced at the application level or via a database function that reads
  `auth.uid()`.
- Add a maximum page offset to `fetchSkills` (e.g., cap at 1000 total results) to
  prevent deep enumeration.
- Consider granting `phone_number` SELECT to `authenticated` only through a dedicated
  view or RPC function that logs each access, rather than via table-level privilege.

### 2. Missing input limits on writable columns — MEDIUM

**Policy / line involved:**

- Migration 20261004, table definition (lines 6-10): `name`, `town`, `description`,
  and `phone_number` are all `text` with no length constraint. `services` is
  `text[]` with no array-dimension or per-element-length CHECK.
- Migration 20261004, INSERT policy "authenticated users can insert their own skill"
  (lines 28-32): `with check (auth.uid() = owner_id)` — validates ownership only,
  not input size.
- Migration 20261004, UPDATE policy "owners can update their own skill" (lines
  35-40): `with check (auth.uid() = owner_id)` — same, no input-size validation.
- `src/lib/skills.ts`, `createSkill` (lines 87-98): passes user input directly to
  `.insert()` with no length validation beyond `.trim()`.
- `src/lib/skills.ts`, `updateSkill` (lines 101-114): passes user input directly to
  `.update()` with no length validation.
- `src/lib/skills.ts`, `parseServices` (lines 40-42): limits the array to 8 elements
  via `.slice(0, 8)` but does not limit per-element string length.
- `src/lib/skills.ts`, `safeSearch` (lines 36-38): sanitizes special characters
  (`% * , ( ) \\`) but does not cap total string length.

**Attack (step by step):**

1. Sign in as any user.
2. Call `createSkill` with a `description` field containing megabytes of text. The
   INSERT policy only checks `auth.uid() = owner_id`, so the oversized payload is
   accepted by the database.
3. Repeat indefinitely — there is no per-user row limit, no quota, and no
   database-level cap on the number of listings a user can create.
4. Call `updateSkill` with an oversized `services` array. While the JavaScript
   `parseServices` caps at 8 elements in the browser, the application exposes the
   raw Supabase client, so a direct API call can send an arbitrarily large array.
   The database has no CHECK constraint on `array_length(services, 1)`.
5. Result: storage exhaustion, degraded query and index performance, and potential
   denial of service against the database.

**Risk:** MEDIUM — resource exhaustion and storage abuse. Not direct data theft, but
can degrade availability for all users.

**Proposed fix:**

- Add `CHECK (length(name) <= 200)`, `CHECK (length(town) <= 100)`,
  `CHECK (length(description) <= 2000)`, and `CHECK (length(phone_number) <= 30)`
  in a new migration.
- Add `CHECK (array_length(services, 1) <= 8)` at the database level to enforce the
  same limit the JavaScript code already uses.
- Add a `CHECK (array_length(services, 1) >= 1)` to prevent empty service arrays.
- Add a per-user quota mechanism (e.g., a database function that counts rows owned
  by `auth.uid()` before allowing INSERT).

### 3. Withdrawn listings have no application-level status filter — defense-in-depth gap — MEDIUM

**Policy / line involved:**

- Migration 20261004, policy "anyone can read active skills" (lines 16-20):
  `using (status = 'active')` — this is the **only** protection preventing withdrawn
  listings from being read. If RLS is bypassed, all rows are exposed.
- `src/lib/skills.ts`, `fetchSkill` (lines 74-78):
  `.select(PUBLIC_COLUMNS).eq("id", id).single()` — no `.eq("status", "active")`
  filter. Relies entirely on RLS.
- `src/lib/skills.ts`, `fetchPhone` (lines 81-85):
  `.select("phone_number").eq("id", id).single()` — no `.eq("status", "active")`
  filter. Relies entirely on RLS.
- Contrast: `src/lib/skills.ts`, `fetchSkills` (line 49): explicitly includes
  `.eq("status", "active")`. This is defense-in-depth; `fetchSkill` and `fetchPhone`
  do not follow the same pattern.

**Attack (step by step):**

1. Any event that disables or misconfigures RLS on `public.skills` (e.g., a migration
   that runs `alter table public.skills disable row level security;`, a project
   restore that does not re-apply policies, or a leaked service-role key used from
   the browser) would expose ALL rows regardless of status.
2. Once RLS is bypassed, `fetchSkill(any_id)` returns all columns for every listing
   — both active and withdrawn.
3. `fetchPhone(any_id)` returns `phone_number` for every listing — both active and
   withdrawn. Unlike `fetchSkills` (which has an application-level `.eq("status",
   "active")`), these functions have no code-level guard.
4. An attacker who triggers or exploits an RLS bypass can enumerate all listing IDs
   (via `fetchSkills` or by trying sequential IDs) and call `fetchPhone` for each,
   harvesting phone numbers of withdrawn listings that owners expected to be hidden.

**Why this is a problem:**

The `fetchSkills` function demonstrates that application-level status filtering is
both possible and used. But `fetchSkill` and `fetchPhone` delegate status filtering
entirely to RLS. This creates a single point of failure: if RLS is ever disabled,
even temporarily, all withdrawn data — including phone numbers — becomes
accessible. The `status` column is also in the `anon` column-level grant (migration
20261007, line 14), so even the existence of status metadata is exposed to anonymous
visitors.

**Risk:** MEDIUM — conditional on RLS being bypassed, but the impact would be HIGH
(full data exposure including phone numbers of withdrawn listings). The absence of
defense-in-depth increases the blast radius of any RLS misconfiguration.

**Proposed fix:**

- Add `.eq("status", "active")` to `fetchSkill` (line 75) for public browsing.
  Users who need their own withdrawn listings should use `fetchMySkills`, which
  already returns all of their own listings.
- For `fetchPhone` (line 82), add an application-level status check: only return
  `phone_number` if the listing is active. If the owner needs to see their own
  phone number for a withdrawn listing, they can retrieve it through a dedicated
  owner-only path (or `fetchMySkills` can be extended to include `phone_number` for
  the authenticated owner, though this changes the PUBLIC_COLUMNS set).
- At minimum, add `.eq("status", "active")` to `fetchPhone` and note that phone
  numbers for withdrawn listings are only accessible to the owner through an
  explicitly scoped query.

### 4. Ownership transfer via update — already mitigated — LOW

**Policy / line involved:**

- Migration 20261004, policy "owners can update their own skill" (lines 35-40):
  ```sql
  using (auth.uid() = owner_id)
  with check (auth.uid() = owner_id);
  ```
  Both the `USING` and `WITH CHECK` clauses are present.
- `src/lib/skills.ts`, `updateSkill` (lines 101-114): the update payload does not
  include `owner_id`, so the application code does not attempt reassignment.

**Attack (step by step — for documentation; blocked by current policy):**

1. Sign in as user A.
2. Attempt to UPDATE a listing owned by user B, setting `owner_id` to user A's UID,
   by calling the Supabase REST API directly (bypassing the application code).
3. **Result: BLOCKED.**
   - The `USING (auth.uid() = owner_id)` clause ensures user A can only target
     rows they already own. User B's listing is not accessible.
   - Even on user A's own listing, the `WITH CHECK (auth.uid() = owner_id)` clause
     ensures the new row's `owner_id` matches user A's UID. If user A tried to set
     `owner_id` to user B's UID, the `WITH CHECK` would fail and the update would
     be rejected.

**Historical context:**

Before the HH-002A commission, the UPDATE policy had only `USING (auth.uid() =
owner_id)` with no `WITH CHECK` clause. This allowed an owner to reassign their
listing to another user by including `owner_id` in the UPDATE payload. The
HH-002A commission added the `WITH CHECK` clause (confirmed in HH-002A-REPORT.md,
"accepted" section).

**Risk:** LOW — ownership transfer is already mitigated by the current policy.
However:

- The application code does not explicitly reject `owner_id` in update payloads
  (the `updateSkill` function simply omits it, relying on the database `WITH CHECK`
  as the sole guard).
- If the `WITH CHECK` clause were ever removed or the policy rewritten, ownership
  transfer would become possible without any application-level warning.

**Proposed fix:**

- No database change needed. The `WITH CHECK` clause is correct and effective.
- Optional: add explicit application-level validation in `updateSkill` to reject
  any payload containing `owner_id`, providing defense-in-depth against future
  policy regressions.
